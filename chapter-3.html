3-06 執行 bash 指令
用驚嘆號進入 bash 模式、Ctrl+B 背景執行、Ctrl+Z 暫時隱藏,決定哪些指令結果要不要讓 Claude 看見。
 ▸

Matt 這堂課把話講得很重:能執行 bash 指令,才是把 agent 從「被動寫程式碼的工具」變成「真正能自己找回饋迴圈、跟專案互動」的關鍵能力。沒有這個能力,Claude 頂多是憑猜測生成程式碼;有了它,Claude 能自己讀 `package.json` 找出 dev server 指令、自己執行、自己看結果修正——這也是為什麼他把這件事放在權限設定(3-07)前面先講,理解執行指令的機制,才有資格談要不要放行。

操作上很簡單:在輸入框打一個驚嘆號 `!` 就進入 bash 模式,這時候打的任何東西都會被當成 shell 指令直接執行,而且結果會被放進 Claude 的 context。Matt 示範跑 `npm run type check`,因為他示範環境沒先跑過 `npm install`,冒出一堆錯誤——但這些錯誤同樣會進到 Claude 的視野裡,於是他接著請 Claude 幫忙處理,Claude 立刻看出 Zod 雖然寫在 `package.json` 裡但沒真的安裝,建議跑 `npm install` 解決。這個小插曲其實示範了 bash 模式最實用的場景:你手動跑一個會出錯的指令,把錯誤直接餵給 Claude,省掉自己複製貼上錯誤訊息的步驟。

但 bash 模式處理不了「跑起來不會結束」的指令,比如 dev server。這時候要在 bash 模式裡先跑 `npm run dev`,趁它還在跑的時候按 Ctrl+B 把它丟到背景執行,畫面上會出現一則「command was manually backgrounded」的訊息,輸出內容則寫進本機檔案,底下狀態列會多出一個背景任務的提示。用方向鍵往下移到這個任務再按 enter,就能檢視這個背景 shell 實際在做什麼——他示範看到 dev server 跑在 localhost:5175,還能按 X 直接停掉它,或按左鍵退回主畫面。這對除錯 dev server 問題特別好用:Claude 能自己看 log、自己送 curl 請求驗證、自己讀懂輸出,不用你在中間傳話。

最後一個工具是完全相反的方向——如果你想跑一個指令但完全不想讓 Claude 看到結果,又想保留 Claude 目前的對話狀態不被打斷,就按 Ctrl+Z 把 Claude Code 整個「掛起(suspend)」。這時候終端機回到普通 shell,你可以做任何事,像他示範的 `echo foo`,Claude 完全看不到;做完之後打 `fg` 就能把 Claude Code 原封不動叫回來。Matt 把整套邏輯收成一句判斷準則:想讓 Claude 看到結果就用 `!` 進 bash 模式,要長駐執行就 Ctrl+B 丟背景,完全不想讓它看見就 Ctrl+Z 掛起——這三條路線,分別對應「共享資訊」「持續監控」「完全隔離」三種不同的協作意圖。

3-07 權限設定
從逐次核准、settings.local.json 到 auto mode 的 LLM 分類器,是把「風險換效率」這件事調到自己舒服刻度的機制。
 ▸

Matt 用一句話點出這堂課的立場:跟 agent 合作永遠要衡量風險與報酬,尤其是你願意放給它多少權力。他直接舉了一個嚇人的例子——如果把 Claude 的權限開到無限大,像很多人做的那樣,你等於是在賭它不會手滑把整個檔案系統刪掉。Claude Code 的解法是一套很細緻的權限模型,預設狀態非常保守:他示範叫它跑 `echo hello`,因為這個指令絕對安全,直接放行;但換成跑 type check(`pnpm type check`),系統立刻跳出確認框,列出確切要執行的指令、它想這麼做的理由(這裡用了 React Router Type Gen 加 TSC),並給出三個選項——這次允許、以後在這個專案裡看到同樣指令都自動允許、或拒絕。拒絕的時候還可以按 Tab 補充理由,比如他示範改口要求改用 `npx tsc`,系統會拿著新指令再問一次。

這些「以後都允許」的選擇不是隨口說說,它們會被實際寫進 `.claude/settings.local.json` 底下的 `permissions.allow` 陣列。這個語法值得花時間搞懂,因為你可以直接手動編輯這份設定,提前把你知道會反覆用到的指令列進去——比如寫死 `pnpm type check` 這一條規則,或者換成萬用字元讓所有 `pnpm` 開頭的指令都自動放行。反過來,`deny` 陣列可以用來明確擋掉危險動作,像他示範的 `git push` 搭配萬用字元,直接封殺所有推送指令,不用每次都手動攔。這套機制不只管 bash 指令,web 搜尋跟網頁抓取一樣要走這個核准流程——他示範叫 Claude 去查 React Router Type Gen 的文件,同樣會跳出核准框,答應之後同一條規則也會寫進 `settings.local.json`。

值得留意的是,`settings.local.json` 在他的專案裡是被 `.gitignore` 排除的,只對他個人生效。如果想把這組規則變成整個團隊共用的預設值,做法很簡單——把檔名從 `settings.local.json` 改成 `settings.json`,這樣就能進版本控制、跟著 repo 一起分享,任何人第一次在這個專案跑 `claude`,都會自動套用同一套權限規則,不必每個人重新手動核准一輪,這對新加入專案的人特別省事。

最後 Matt 介紹了他個人現在的預設模式:auto mode。用 Shift+Tab 可以在 manual(逐次核准)、accept edits(自動接受編輯)、plan mode、auto mode 之間切換。Auto mode 的機制是用一個 LLM 分類器(他猜是 Haiku)在動作執行前先評估這個指令安不安全,安全就直接放行不用你介入——他示範跑 `npm run type check`,不用任何手動核准就直接執行了。這個機制的代價是會多花一點 token 跟一點時間讓分類器判斷,而且分類器不是完美的:他坦承有時候資料庫遷移這種危險動作被放行,反而建立 GitHub issue 這種正常動作偶爾被卡住。即便如此,他認為整體抓得「剛好在可接受的那一側」——真正危險的操作(像不小心 `rm -rf` 整個檔案系統)幾乎都會被擋下,而且不太會把使用額度衝高太多。更重要的是 `settings.json` 跟 auto mode 不是互斥的,harness 會先檢查 settings 裡有沒有現成規則,沒有才會丟給分類器判斷,所以把常用指令寫進 settings.json,等於幫 auto mode 分流減負。這個預設值可以到 `/config` 裡找到「default permission mode」設定起來,Matt 自己就是把它固定在 auto mode——這也解釋了為什麼你之後在課程示範裡很少看到他被權限彈窗打斷。
