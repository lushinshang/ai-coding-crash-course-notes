第2章 核心概念 · 2-07

這樣花了多少錢

帳單為什麼看不懂：拆解 input token、output token、快取寫入與快取讀取的計價邏輯。
5倍
output token 比 input token 貴
1/10
cache read 對比基礎 input 的價格

帳單看不懂，不是因為算法藏得多深，是因為成本分散在 session、turn、model provider request 三層裡——你能看到帳單往上跳，卻很難說清楚到底是哪個動作讓它變貴。把黑盒子拆開的方式，是回到最基本的兩個數字：每次 model provider request，送出去的是 input token，收回來的是 output token，而 output token 的計價通常貴上好幾倍——以 Claude Fable 5 的 API 價格為例，input 一百萬 token 十美元，output 卻是五十美元，整整五倍。但反過來，output 通常只有幾百個 token（一個工具呼叫、一段簡短回覆），真正撐大帳單體積的是 input，因為 input 等於目前為止整個 session 的內容。

實測給你看快取（cache）怎麼運作最能說明問題。第一句「hello」，log 顯示 input token 只有兩個，但底下多了 cache creation input tokens 這一項——系統提示那一大包文字被寫進了 prefix cache（前綴快取），這次是「寫入」，還沒享受到折扣。緊接著第二句「tell me you like my shirt」，這次 log 顯示讀到了兩萬多個 cache read token，只補寫了 59 個新的——快取已經預熱，之後每次請求都是在讀已經算過的東西，而快取讀取的計價是基礎 input token 的十分之一。這解釋了為什麼 session 是「靠往後疊字」在成長的：每次請求都是前一次請求原封不動加上新的一小段，正好吃到快取機制的紅利，也是為什麼很少變動的內容會被放在請求最前面、常變動的內容放在後面——這是配合快取行為設計出來的，不是巧合。

真正該留意的提醒是：這套機制看似讓對話越長越便宜，其實反過來會製造陷阱——session 一開始塞進去的任何一個 input token，之後每一次請求都要重新算進帳單裡，就算靠快取打折，那個折扣後的成本還是會一次又一次地疊加。早期就堆進 context 裡的雜訊，會像沉積物一樣一路被付錢付到底。這句話直接呼應聰明區與笨蛋區的核心結論：保持 context 精簡、保持內容跟任務相關，不只是為了讓模型維持在聰明區，同時也是在替錢包省錢——這兩件事其實是同一個決定的兩面。
