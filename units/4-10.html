交接 handoff

compaction 出不了同一個 agent、同一個資料夾，這時候把 session 寫成一份可攜的 handoff.md，什麼人什麼工具都能接手。
89K
觸發 handoff 前的 token 使用量

compaction 有一個沒講出來的前提:新 session 必須跟舊 session 待在同一個 agent、同一個目錄裡。這個限制平常不會有感覺,直到你想做一件很自然的事——用一個 agent 寫完一個功能,想換另一個工具來做 review,結果發現 compaction 完全用不上,因為它是在 harness 記憶體裡運作的內部機制,換了 agent 就等於換了記憶體。

與其把摘要壓縮在 harness 內部的記憶裡,handoff 把同樣的摘要動作寫成一份 handoff.md,一份完全可攜的 markdown 檔。這份檔案不綁定任何 agent、任何目錄,可以餵給另一個工具、傳給另一個目錄裡的 agent,甚至直接寄給同事——它本質上已經脫離了對話本身,變成一份獨立文件。實際操作時,在舊 session 打 `/handoff`,後面接一句交接理由(就像 compact 也需要理由一樣),skill 會要求寫入使用者作業系統的暫存目錄,產生一份細節豐富、附帶大量檔案參照的文件,內容形態跟 compaction 產出的摘要相當接近。新 session 這邊只要打開一個全新視窗、清空對話,用 `@` 符號找到 temp 目錄下那份 handoff 檔案,一引用進來,內容就立刻讀進 context window,可以馬上接著審查或動工。

這些 handoff 文件被刻意設計成閱後即焚——存在暫存目錄,不會留在專案裡,不會進任何記憶系統,電腦下次重開機或作業系統清暫存目錄時就會消失。這個設計選擇很說明 handoff 的定位:它不是要取代 compaction 的長期記憶功能,而是解決一次性的跨 agent、跨目錄傳遞問題。一個很實際的情境是:在改一個功能,途中撞見一個完全無關的 bug,不想現在處理也不想忘記,直接生一份 handoff 檔,晚點開新 session 接手處理就好——不用中斷手上的工作,也不用把無關的上下文硬塞進同一個對話。

所以兩者不是替代關係,而是分工。留在同一個目錄、只是想保留前一段對話的脈絡、還打算接著排隊丟訊息,compaction 依然是更好的選擇;一旦要跨 agent、跨目錄,或者這份摘要根本是要給另一個人類看,才輪到 handoff 上場。代價是 handoff 銜接下一段對話的動作比較繁瑣——得自己去暫存目錄把檔案找出來、手動引用進新 session,不像 compaction 那樣在同一條對話線裡無縫接軌。
