spec 該留著嗎

spec 是次要來源、會跟程式碼漂移，實作完就該關閉存檔，不當成長期文件留著。

這堂課回答一個大家常問的問題：spec 都寫進程式碼了，還要留著它嗎？當作文件保存、或者留一份歷史紀錄不是挺好的嗎？Matt 的答案會讓不少人意外——他選擇把 spec 關閉存檔。

他的論證核心是「主要來源 vs 次要來源」的框架：spec 是程式碼運作方式的濃縮版本，屬於次要來源，而次要來源必然只是一種投影、一種摘要，一旦你沒有持續讓它跟著程式碼同步更新，兩者就會開始漂移。市面上有一派流行做法叫「spec-driven development」，主張把 spec 存進 repo 當成真理來源，但 Matt 說正是這種漂移風險讓他不敢這麼做——因為 agent 探索本機 repo 時，遇到一份過時但看起來完整的舊 spec，很可能會信任這份好讀、精簡的次要來源，而不會去碰更囉唆、更難探索的主要來源，也就是程式碼本身。程式碼不會對自己說謊，可執行的部分（函式本身）幾乎不可能謊報自己在做什麼，除非你的 repo 裡本來就有一堆沒人呼叫的死程式碼。

所以他的建議是：spec 一旦被落實進程式碼，就該立刻關閉。這正好呼應 6-02 把 spec、ticket 放進 issue tracker 而不是本機 markdown 檔的決定——issue 一關閉，它就自然從主要視圖移出、被標記為封存，但如果之後 agent 真的需要回頭查某個功能當初為什麼這樣設計，這份紀錄還在，可以被找到、被探索。而且放在 tracker 裡的 spec 是整個團隊共享的、可審查可留言、就算你換了工作目錄或換了筆電，這份狀態也不會跟著本機環境流失。

他把話說得很重：spec 是暫時的產物，用來界定一段工作的範圍，不是程式碼運作方式的真理來源。這個立場跟不少強調「spec 即真理」的框架正面衝突，他也大方承認這點可以辯論，但根據他自己的實測，把 spec 當長期真理來源留在 repo 裡，效果並不好。
