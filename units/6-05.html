第6章 把功能出貨 · 6-05

執行你的 ticket

implement skill 串起 TDD 和 code review 兩個子技能，一張票一個乾淨的 session。
90K
tokens 時選擇清空 context

spec 定了目的地、ticket 拆好了路線，這堂課終於要動手把票實作出來。負責這件事的是 implement skill，但它本身其實很單薄，大部分工作都委派給另外兩個 skill：TDD 和 code review。

TDD 這塊他講得很直白：agent 表現最好的時候，就是拿到最多回饋的時候。所以實作新功能時，先寫單元測試、再實作，這個順序本身就是在給 agent 製造回饋迴路。TDD skill 裡面還帶了不少細節——什麼叫好測試、怎麼用 mock、只在「約定好的接縫」（pre-agreed seams）上測試、什麼叫「同義反覆」（tautological）的爛測試——但他說你不需要背熟這些，這個 skill 本身就是提升程式碼品質的一記重拳，接住就是了。

code review 這塊更值得細看。它做的是兩軸審查：一個子 agent 對照一組標準去檢查，另一個子 agent 對照原始 spec 去檢查，藉由拆成子 agent 分頭進行，Matt 說這種自動化審查大幅提升了輸出品質，而且常常會直接把明顯的爛東西修掉，你只需要「審查那份審查結果」就好。至於這道審查要放在每張票做完之後、還是全部票做完再一次做，他坦言是個可以討論的取捨；示範裡選擇每張票做完就審一次。

實作流程上，他把每張 ticket 的連結複製給 implement 指令，做完一張就照 6-04 那套判斷框架決定 clear、compact 還是繼續，並且把 issue 關掉——這是個好習慣，因為關掉第一張票，被它擋住的第二張票才會解鎖。值得注意的是，他在規劃完（spec、ticket 都定案）之後選擇直接 clear 掉整個對話進實作階段，理由是規劃階段的討論內容已經被編碼進 spec 和 ticket 這兩份「context 之外」的文件裡了，留著反而是更囉唆版本的重複資訊，不如清乾淨、把整個 smart zone 讓給接下來的實作。這正好呼應了 6-02 為什麼堅持要把 spec、ticket 放進 issue tracker 而不是本機——它們才是真正跨 session 存活的記憶。
