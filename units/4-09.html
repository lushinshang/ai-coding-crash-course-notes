第4章 基本功 · 4-09

compaction 壓縮

快滿的 context 不是硬撐也不是全清,而是把整個 session 壓成摘要、開新局繼續打。
150K → 28.3K
compaction 後 token 用量大幅下降

一段對話開太久,通常會走到兩條死路的其中一條。繼續下去,context 塞滿了不相干的檔案讀寫痕跡,agent 開始在「dumb zone」裡運作——回應變慢、變笨,而且因為每次 request 都要把之前所有 token 原封不動送出去,就算已經是 cached 價格,還是持續燒錢。另一條路是直接清空 context,重新開始,但這其實更浪費:agent 得從零重建對前一輪工作的理解,你得重新解釋「這段程式碼為什麼存在」,而那些在初始對話裡被你盤問出來的關鍵決策脈絡,很可能就這樣消失了。

真正該做的不是保留全部,也不是全部丟掉,而是把舊 session 壓縮成摘要,拿去開一個新的 session。這個動作可以想成「反過來的 subagent」——不是派一個 subagent 出去做事再回報,而是在你自己掌控的兩個 session 之間做交接,一個把歷史記下來,另一個接手繼續做。這個技巧就叫 compaction:下指令的方式很單純,在 Claude Code 打 `compact`,還可以附上一句話告訴它要摘要哪些重點——例如「我們接下來要對這段剛做完的東西做 QA」。這句提示不需要多詳細,但很有用,因為執行摘要的本質仍是一個語言模型在讀完整段對話後做取捨,你給的方向愈明確,它就愈知道哪些細節該留下來。

壓縮出來的結果相當驚人:一段原本 150K token 的對話,壓完只剩 28.3K token,直接把你送回 smart zone 裡有大量餘裕可以動用的狀態。而且它不是無腦砍字——摘要裡除了會保留主要需求與意圖、關鍵技術概念這類敘述性重點,還會挑出幾個它判斷對下一階段仍然重要的檔案,以接近逐字的方式原封不動留在 context 裡,而不只是提一句檔名了事。

不過這個效率是有代價的,而且代價的性質可以用歷史學的方式理解:原始 session 是第一手史料,是當時所有人親身經歷、留下的完整記錄;compaction 產生的摘要則是第二手史料,是一段有損壓縮。任何形式的交接機制都逃不掉這個取捨——只要創造出一份摘要,就一定在丟資訊,換來的是效率:繼續留在第一手來源裡,擁有全部細節但夾雜大量噪音;換到第二手摘要,多出大量可操作空間,卻可能漏掉某些原始對話裡的細微語氣或未明說的判斷依據。也因此 compaction 不是萬用解——但像「對一段剛完成的工作做 QA」這種場景,原始探索過程本身沒有太大留存價值,是壓縮技巧派上用場最理所當然的時機。
