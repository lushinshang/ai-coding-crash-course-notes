模型、harness、agent、環境

拆解 agent 的四個零件，破解「換模型就能變強」的迷思，把注意力導向可控的系統設計。

多數人學 AI coding 是從認識模型開始的——Opus、Sonnet、GLM、Fable，一個個響亮的名字先進場，彷彿只要換到更強的那一個，一切就會變好。但拆開 agent 這個東西的內部結構，會發現模型其實是這套系統裡地位最小的零件。

它只是引擎。一個接收文字、吐出文字的無狀態機器，自己什麼都做不了，連存個檔案都不行。真正讓它能寫檔案、跑指令、查網路的，是包在外面的 harness，而 harness 本身還不夠，它必須綁定一個具體的環境才有意義——Claude Code、Codex 綁的是檔案系統，ChatGPT、claude.ai 綁的是它們自己那套虛擬環境，能存文件、能搜網頁，但終究不是真實的磁碟。model 加上 harness，在某個環境裡運作，這整組合起來才叫做 agent——agent 不是一個獨立實體，只是「harness 包著 model，在環境裡跑」這件事的代稱，拿掉任何一個零件，這個詞就不成立。

這個拆解看起來只是命名遊戲，但它其實是整門課的座標系。後面要講的 context window、聰明區笨蛋區、無狀態、幻覺、subagent，講的全部都是同一件事：harness 和環境可以怎麼被設計，好讓同一顆引擎跑得更好。這個框架的真正用意，是把注意力從「哪個模型最強」移開——訓練一顆新模型是絕大多數人一輩子碰不到的門檻，但調整 harness、優化環境，是今天下午就能動手做的事。

這個比喻並不完美，連它本身都承認——一個 npm script 算 harness 的一部分還是環境的一部分？見仁見智，harness 跟環境之間本來就有模糊地帶。但這不影響核心結論：當有人喊著「只要換成某某新模型，一切都會變好」，這種唯模型論低估了系統裡其他零件的份量。性能瓶頸更常出現在 harness 和環境的設計上，而不是引擎本身——這句話會在後面「怎麼選模型」那堂被具體量化成「50/50」的比例，值得先記下來對照。
