第4章 基本功 · 4-07

plan mode 為什麼不好用

plan mode 只是把「急著生出成品」的毛病從程式碼搬到計畫文件,本質沒解決。

上一堂跑出來的結果其實還不差,但真正讓人不安的地方在別的地方:prompt 一送出去,agent 探索完 codebase 就立刻開始實作,中間沒有任何跟人類對齊的環節,純粹是走運才做出接近預期的東西。這種「急著生出東西」的傾向是 agent 的一種諂媚特質——你說你想要什麼,它就衝去做出那個東西,不會停下來確認它理解的跟你要的是不是同一回事。

於是拿多數 harness 內建的解法來測試:plan mode。操作上用 `npm run reset` 回到乾淨狀態,切到 dev branch,shift-tab 幾次切進 plan mode,貼上同一句 prompt。理論上這應該像個緩衝區:先探索、寫成一份計畫文件、讀完覺得 OK 才繼續實作。但實測下來,plan mode 只是把問題往前挪了一步——它一樣急著把探索結果趕製成一份讀起來就像實作細節的計畫書,本質上還是同一種急著生出成品的衝動,只是產出從程式碼換成了文件。

《The Design of Design》裡 Frederick Brooks(《人月神話》作者)有個概念值得借用——設計概念不是一份資產,而是人在討論設計時,腦子裡那個逐漸清晰、大家透過對話慢慢對齊的東西。plan mode 跟前一堂的素樸做法一樣,都缺了這個「彼此對齊」的過程,只是生出一份看起來很正式的文件,並沒有真正核對過雙方理解是否一致。對這種簡單功能來說問題不大,但功能一旦複雜起來,這種假對齊很快就會出事,做出完全偏題的東西。

這堂課是承先啟後的轉折:先否定了兩條看似合理的路——素樸實作、plan mode,然後把懸念丟給下一堂:針對這個具體、已經被示範出來的失敗模式,還有沒有真正解決的做法。
