自動 compaction

Harness 內建的自動壓縮能保底不爆 context，但在階段中途硬壓縮，往往換來風格跑掉、忘記需求的代價。
250,000
settings.json 可自訂的 auto-compact 觸發門檻範例

當一個 request 送到模型供應商,裡面塞了超過上限的 token,結果不是模型努力擠出回應,而是直接報錯——模型本身完全沒有能力處理超出 context window 的內容,這是個硬限制,不是軟性建議。正因為每一家 harness 都會撞到這個牆,所以每一家 harness 都內建了同一種保護機制:當 session 逼近上限時,自動幫你 compact。在 Claude Code 裡,這個開關就在 `/config` 裡的 auto-compact,預設是開啟;想自己調整也可以,進到 `.claude` 目錄下的 `settings.json`,把觸發門檻改成任何想要的數字,例如 250,000 個 token。

自動 compaction 聽起來像是解方——如果它真的完美,就再也不用管 phase boundary、不用管 smart zone,那整套「什麼時候該收斂、什麼時候該交接」的決策樹根本不需要存在,系統會自己在對的時間點幫你壓縮。但事實是,自動 compaction 是一個極難解決的問題,而且一旦做錯,代價非常慘痛。想像把 grilling 階段和 implementation 階段之間畫一條 phase boundary,如果系統硬性規定你必須在 session 裡的某處塞入一次 compact,最安全的位置顯然就是這條分界線——因為如果 compact 發生在 grilling 進行到一半,後半段面對的就只是前面討論內容的摘要,而不是完整脈絡。

在 implementation 階段,這個問題只會更嚴重。一旦 compact 發生在實作進行到一半,agent 常常會徹底迷失方向,後半段程式碼會突然換一套完全不同的風格,甚至整個忘記原本該實作的功能。在 phase 中段隨機觸發的 compact,幾乎必然導向更差的程式碼結果——這正是自動 compaction 最大的陷阱:它沒有時機的概念,只認 token 數字,不認工作到哪個階段。另一個常被忽略的細節是,自動觸發的 compact 完全沒有給你機會說明「這次該保留什麼、下一段 session 的意圖是什麼」,而那段手動寫給 handoff 或 compact 的摘要說明,恰恰是決定壓縮結果好壞的關鍵。

所以與其把「什麼時候該收斂」這個決策權交給 harness,更好的做法是人類自己掌握它:自己決定要繼續、要清空、要 handoff、要丟給 subagent,還是要手動 compact,而且永遠選在 phase boundary 上做,而不是任由系統在 phase 中段隨機出手。這是一次性的學習曲線,一旦練成,session 會更常落在 smart zone 裡,結果也會越來越穩定——如果常常撞到 auto-compact 的門檻,那通常代表某個環節已經出了問題,而不是代表系統正在幫你。這也是整個第 4 章一路鋪陳下來的骨幹收尾:context 清理打地基、探索與理解建立能力、對齊而非急就章確立心法、compaction/handoff/決策樹提供具體工具,最後提醒的是,即使 harness 提供了看似省事的自動化,身為操盤手的人,還是得繼續握著方向盤。
