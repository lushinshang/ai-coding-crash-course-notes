第6章 把功能出貨 · 6-09

讓 AI 遵守你的程式碼規範

用 coding-standards.md 餵給 code review 的子 agent，比塞進 CLAUDE.md 或硬求實作一次到位更有效。

6-05 implement skill裡有一行話被 Matt 刻意帶過去沒細講——「做完之後用 code review 審查」，這堂課回頭把這句話攤開講清楚，順便講怎麼用這個 skill 把你自己的程式碼規範塞進 agent 的審查流程裡。

他先給了一個三層檢查的框架：第一層是自動化檢查，也就是 lint、type check、單元測試，這些是決定性的，agent 跑出來永遠是同樣的通過或失敗，幾乎不花 token，是免費的。但自動化檢查抓不到所有 bug，需要某種形式的審查系統——在 AI 之前這是人工 code review，人會提供質化的回饋，像是「這個測試好像沒測到重點」「有沒有考慮過這個做法」，而人工 review 向來是開發流程裡最讓人痛苦的一環，PR 堆積如山等審。現在 agent 能做自動化審查、提供這種質化回饋，但 Matt 強調這不能取代人工審查，只是讓人工審查輕鬆一點，因為 agent 已經先過了一輪。

真正的重點在後半段：coding-standards.md。他的邏輯是，implement 這個角色本身受到很多限制——要先探索 repo、要真的把功能寫出來、還要除錯確認能跑，負擔很重；相對地 code review 不需要重新探索（探索已經做完了）、拿到的就是正確的檔案、需要改的地方通常不多，測試也早就寫好跑過了。負擔輕，代表 context window 裡有更多空間可以塞規範細節。所以與其硬逼 implement 一次到位把規範刻進腦子裡，不如把規範放進 code review 讀取的 coding-standards.md，讓審查這一關去抓。他秀了自己在 course-video-manager repo 裡的實際範例，裡面條目多半是「踩過的坑」——像是「情境選單項目一定要帶前導圖示」，就是因為以前 agent 老是漏掉圖示他才加進去的；「app routes 底下的所有檔案都會被公開路由，不要放測試檔或工具檔在那」也是同樣邏輯。他甚至提到就算你完全不寫 coding-standards.md，code review skill 本身也內建了一批取自 Martin Fowler《Refactoring》的程式碼異味（code smell）判準，像 feature envy、shotgun surgery，agent 對這些經典術語本來就熟。他給的實用建議很具體：下次看到 agent 做出你不喜歡的事，不要當場罵它，把規則寫進 coding-standards.md，讓審查那關下次抓到它。
