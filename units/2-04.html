session 與 context

幫上一堂看到的巨量文字取名叫 context，並定義了「session」這個之後要一直拿來操作的單位。
1.1M tokens
GPT 5.6 Sol context window
1M tokens
Gemini 3 Pro context window
128K tokens
GPT 5.2 chat latest context window

上一堂翻 log 時刻意迴避了一個大家都很熟的詞，這堂課把它補上：那一大坨系統提示、工具定義、歷史對話，全部合起來就叫做 agent 的 context（上下文）。這不是修辭補充，是把「turn」跟「這包文字」正式接起來——模型每次預測下一個 token，靠的就是把整包 context 轉成 token 丟進去運算，排行榜上「context window 一百萬 token」那個數字，講的正是這包東西能塞多大。但這個數字是廠商依照自家模型和基礎設施「大概能撐多少」訂出來的相對武斷上限——超過就直接失敗，一個輸出 token 都拿不到。

context window 從來不是從零開始的，這是容易被忽略但很重要的一點。一啟動 harness，它就已經預先塞了一堆東西進去——工具清單、角色設定、行為規範，這一整包叫做 system prompt（系統提示）。像 Claude Code 的系統提示片段會寫著：「你是 Claude Code，Anthropic 的官方 CLI……協助已授權的安全測試……拒絕破壞性技術、阻斷服務攻擊」——這些話從沒被使用者打過，卻在每一次對話裡先墊在最底下。這說明了為什麼「選 harness」本身就是一個影響很大的決定：不同 harness 塞進去的起始文字量差很多，起跑點根本不一樣。

真正要交付的字，是 session（會話）。多個 turn 疊加起來、context 不斷累積的整個過程，就叫一個 session——第一個 turn 有五次 model provider request，第二個三次，第三個四次，最後一次請求送出去的，就是目前為止全部的對話歷史。這個詞之所以重要，是因為它馬上會變成一個可操作的單位：可以清空 context 開新的 session，可以做 compact（壓縮），也可以切到別的 session 之後再回來。session 裡塞的東西越多，會發生什麼事？答案不會是好事——這正是下一堂要拆解的東西。
