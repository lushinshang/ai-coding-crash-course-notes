第5章 引導技巧 · 5-02

用指標來引導

用資料庫遷移的真實坑,示範把該塞進 push 的規則改造成 doc + pointer。

延續上一集的理論，這集直接進到一個真實案例：這門課的專案裡,每次改資料庫 schema（新增或修改表）都必須連動修改 seed.ts,否則重新產生資料庫時會留下跟實際 schema 對不上的髒資料。這種「兩件事必須綁在一起做，卻在程式碼裡完全看不出關聯」的知識，正是新人第一天要靠人口耳相傳教的那種東西，agent 也一樣沒辦法從程式碼本身推匯出來，所以是典型「值得塞進去」的資訊。

Matt 先示範最直覺但錯誤的做法：把整套遷移步驟直接寫進 agents.md（push），然後用 request logger 實際抓封包給你看——你會看到這段文字被包在一段 system reminder 裡送進每一次 request，前面寫著「important, these instructions override any default behavior」，但底下 Claude Code 自己又加了一句「this context may or may not be relevant to your task, you should not respond to this context unless it is highly relevant」。這個細節很值得注意：Anthropic 自己也知道大家把 agents.md 塞爆的問題,才加了這句免責宣告,這也解釋了為什麼很多人抱怨 claude.md 裡寫的規則不一定會被遵守。

問題是：這套遷移步驟不是每次工作都用得到。很多功能改動根本不碰資料庫，QA session 也用不到，硬把它 push 進去等於每個 turn 都在燒不必要的 context load。所以他的解法是把這段詳細步驟搬出 agents.md，放進 repo 根目錄新建的 docs 資料夾裡，agents.md 裡只留一行 context pointer（「當你要動 schema 的時候，去讀這份檔案」），這就是這章會反覆出現的「doc + pointer」模式。

這集也第一次帶出「writing for agents」這個 skill——一個專門用來寫 agents.md、寫 skill、寫給 agent 看的檔案的工具，Matt 說自己寫檔案、寫 steering 規則時都靠它。這集本身是練習題（作業嚮導讀），要你自己動手把大段規則搬到指標背後，再用一次實際的 schema 改動去驗證 agent 真的會去把那份檔案拉進來——這個驗證動作直接對應鐵律裡「驗證後才能說完成」的精神，也是為 5-03 引入 Agent Skills 鋪路：doc + pointer 做得再好，也還有一個致命限制沒解決，那就是下一集要談的「不能打包帶走」。
