第6章 把功能出貨 · 6-02

設定你的 issue tracker

把 spec 和 ticket 都搬出本機、放進 GitHub issue，讓人和 agent 共用同一份任務清單。
1,200
已關閉的 issue 數
28
仍開著的 issue 數

這堂課回答一個很實際的問題：spec 和 ticket 這些文件到底該放哪裡。Matt 的答案很明確——不要放在 repo 裡的本機檔案，而是放進 repo 外部的 issue tracker。理由也很直白：issue tracker 本來就是團隊之間協調工作用的東西，而 agent 現在可以透過 CLI 直接讀寫同一份 issue，等於把 AI 也變成團隊裡能收派工單的一員。他自己的主力 repo 就是這樣運作的，1200 個 issue 關閉、只剩 28 個開著，可見這套機制他是真的每天在用來排程自己的工作，不是課程裡臨時包裝出來的示範流程。

課程選 GitHub 純粹是因為好裝、免費、多數人本來就有帳號，但他也講得很清楚，這一整套概念換成 Jira、Linear、Todoist 都成立，重點是「issue tracker 是 agent 和人共用的介面」這個原則，不是綁死在特定工具上。要跟 agent 溝通，本機端要先裝好 GitHub CLI，這是 agent 從你的機器連到 GitHub 抓 issue 的橋樑。

操作上他要你先 fork 他的課程 repo（用 `npx ai-hero-cli fork`），原因也很實在：如果大家都在同一個 repo 開 issue，那彼此的測試 issue 會全部混在一起，變成一場災難。fork 出自己的私有 repo 之後，再用 `npm run reset` 拉一個叫「set up MacPoco skills」的 skill 進來，跑起來後它會探索 repo 現況，問你要用哪個 issue tracker，選 GitHub 之後，它會在 `agents.md` 裡加一個導航指標，告訴 agent「issue 和 PRD 都在 GitHub issue 裡，用 GitHub CLI 管理」。這個小小的設定動作，就是接下來整章工作流程能運作的地基——沒有這一步，spec 和 ticket 就無處安放。
