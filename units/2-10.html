怎麼選模型

模型只佔整個系統的一半分量——具體的 50/50 判斷，並教你怎麼建立自己的模型直覺。
50 / 50
模型 vs harness+環境 的重要性佔比

「這個新模型完爆所有對手，你不用就等著被淘汰」——這種風氣值得被潑一盆冷水。這堂課要做的事，是把模型、harness、環境那張架構圖量化成一個具體的比例：模型大概佔整個系統重要性的一半，不多不少，50/50，跟 harness 加環境那一側打平。這句話同時否定了兩種極端：既不是「模型不重要，隨便選都行」，也不是「模型就是一切，其他都是細節」。換成一個很爛的模型，系統照樣廢掉；但如果模型本身已經夠好，接下來能榨出的改善空間，往往在 harness 和環境裡。

判斷該選哪個模型，有兩個維度。第一個是效率：不能只看 token 花了多少，要看這些 token 換到了什麼。排行榜圖表上，Gemini 3.5 Flash 花了很多 token 卻沒換到太多產出，但因為它每個 token 的單價便宜，換算下來反而落在效率不錯的區域——便宜模型可能靠走量打平品質差距，貴模型如果每個 token 都算得精準，也可能比較划算。而且選的不只是模型，還連帶選了一套計價結構——API 逐 token 計費，跟訂閱制的每月吃到飽，實際成本可以差很多。第二個維度是任務需要的品質等級不同：探索、研究、摘要這類工作，低 effort 可能就夠用；但詳細規劃、程式碼審查這種需要深度推理的任務，拉高 effort 帶來的分數提升才是真的有感——這時候值得考慮用不同模型分工，比如規劃階段用 Fable medium，落地實作階段用 GPT 5.6 Sol medium。

任何排行榜、任何 benchmark 圖表，終究只是別人任務集合上的分數，跟每天實際在做的工作不見得對得上。真正的建議是把模型當成員工來理解：員工會來來去去，真正能長期發揮價值的，是有沒有投資公司的基礎建設——也就是 harness 和環境，讓任何一個新進員工都能上手發揮。要摸清楚一個模型的脾氣，唯一辦法是實際用過、盯著帳單看、憑經驗建立自己的模型排序，而不是照抄別人的圖表。後面課程會教一套更 empirical（更貼近經驗值）的評估方法——拿同樣的輸入，換兩套不同的模型或 effort 設定，實測比較哪個表現更好，這比看排行榜可靠得多。整堂課收在同一個立場：選定一個順手的模型和 effort，好好把它摸熟，別把時間耗在不斷 min-max 切換上——這正是上一堂丟出的判斷，在這裡被講得更完整。
