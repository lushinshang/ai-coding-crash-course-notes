如何應付龐大任務

用 spec 定目的地、用 ticket 拆路徑，把超出單一 context window 負荷的野心之作拆成能交付的份量。
30
他處理過最大的 spec 底下掛的 ticket 張數

到這裡，你已經被灌輸了一種近乎偏執的習慣——時時刻刻盯著 context window，分辨自己現在站在 smart zone 還是已經滑進 dumb zone。這套習慣在單一個 session 就能做完的工作上很夠用：改個小功能、修個 bug，一路從頭做到尾，盯緊這條線不要跨進 dumb zone 就好。但真正龐大的工作根本不是這麼一回事——一次會動到整個應用程式每一層的重構，或者你光看任務描述就知道連塞進一整個 context window 都不夠，更別說擠進 smart zone。這種規模的工作，要怎麼一次交出去？

答案不是什麼新發明，而是軟體工程師做了幾十年的老招：把大任務拆成一個個小塊，每一塊都小到能完整塞進 agent 的 smart zone。問題是拆完之後，規劃這件事本身也變了——在這之前，計畫的有效期限就是一個 context window 的長度，從沒認真想過如果工作要橫跨多個 session、多個 context window，前置的規劃該長什麼樣子。

這套摸索出來的做法靠兩份文件撐起來。第一份描述目的地——你到底要抵達哪裡；第二份則把抵達那裡的路徑拆成一張張 ticket，一張 ticket 對應一個能塞進 smart zone 的工作份量。如果目的地要拆成四塊，你就會得到一份 spec 加四張 ticket，每一張 ticket 本身就是那個 session 的實作計畫。這樣拆開來的好處是規模可以放得很大——他自己就處理過底下掛了 30 張 ticket 的巨型 spec，一路做下來還是撐住了。

這也是整個章節接下來要展開的主軸：用 spec 定目的地、用 ticket 切路徑，把原本超出單一 context window 負荷的野心之作，拆成一段段可以真正交付的工作。
