clear、compact、handoff 還是 subagent

一張決策樹，把清空、壓縮、交接、丟給 subagent 四條路配上判斷條件，收束前面幾堂學到的所有招式。
30K
grilling 結束時的 token 量,足以直接接續 implementation
150K
implementation 完成後的 token 量,改用 subagent 做審查
5
階段邊界上可選擇的動作:繼續、清除、compact、handoff、subagent

grilling 結束時,context 才用掉 30K tokens,很自然就直接接著做 implementation——因為 implementation 需要 grilling 過程裡那些探索與決策的原始推理,中途切換只會製造二手資訊的失真。可是 implementation 做完準備進 QA 時,同樣是一個「階段結束」的時間點,這次卻選擇了 compact。分岔點的關鍵不在於某個階段是否結束,而在於下一個任務用不用得到這段 context,以及手上還剩多少 smart zone 額度。同一種情境「階段邊界」,可以導出完全不同的動作,這正是這件事沒有標準答案、需要一套判斷框架的原因。

在每個階段邊界上,實際能做的事只有五種:直接繼續、清空 context 重開一個 session、compact 之後把摘要餵進新 session、handoff(把目前 session 寫成一份 markdown 檔案往外傳)、或是丟給 subagent 去處理再回報結果。判斷的第一關是「能不能繼續」——如果下一階段需要這一階段的第一手推理(例如 grilling 接 implementation),或是 token 用量還在低檔、任務也不大,那就沒有理由中斷。真正要中斷時,下一個問題是「這段 context 對下一個任務還有沒有用」:如果完全用不到,清除 context 是所有選項裡代價最低的一個——它不花時間,單純刪除資訊,換來的是最大的 smart zone 額度,但前提是這個 session 裡的探索與決策必須是完全可拋棄的。一旦清掉的是有用的資訊,例如拿掉 implementation 前的 QA 卻連帶清掉了 grilling 階段做決策的理由,QA 就會失去判斷依據,這時候清除就不是選項。

如果 context 是相關的、不能清掉,決策樹接著問「需不需要 handoff」。handoff 的用途相對窄:只有當你要把工作真的交到另一個 agent、另一個目錄、或另一位協作者手上時才需要寫這份摘要檔案,也適合用在階段進行到一半、臨時發現另一個需要處理的支線任務、想暫時分身去處理但不想打斷主線的場合。排除掉 handoff 之後,下一題是「這個任務能不能 AFK(away from keyboard)完成」——也就是人完全不用介入,任務範圍夠明確,agent 自己就能跑完。只要人類不需要在場介入,把任務丟給 subagent 去跑,就能讓它在自己的 context window 裡工作,完全不動到 main session。具體的例子是 implementation 做完、token 已經到 150K 時的自動化審查:可以選擇 compact 後在 main session 裡做審查,但因為這個審查階段不需要人在場,更合理的做法是直接開一個 subagent 去跑,審查結果回報回來就好。

把「繼續」「context 不相關」「需要 handoff」「能 AFK」這四個問題都問過一輪,剩下的情況就是決策樹的預設出口:compact。也就是 context 相關、不能直接繼續、不需要 handoff、任務又得要人在場處理的時候,compact 就是答案。這些判斷準則本質上帶著主觀成分與品味,答案會隨經驗慢慢長出來,不是一套可以死記硬套的規則,而是一種需要在實戰裡反覆校準的直覺——也直接為下一堂「自動 compaction 好不好」鋪路:既然人可以在階段邊界上做出這麼細緻的判斷,那把這個判斷丟給 harness 自動處理,會發生什麼事?
